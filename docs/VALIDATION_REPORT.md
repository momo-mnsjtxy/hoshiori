# 真机验收报告

日期 2026-11-01。第一次在真卡上跑，环境：RTX 5090 D（32 GB，sm_120）、驱动 595.71、Ubuntu、Python 3.12.3、torch 2.8.0+cu128、bitsandbytes 0.50.2、25 核、754 GB 内存。

远端仓库 `/root/hoshiori`（本地 tar 推过去，与本地同一提交），`pip install -e .` 后全量测试 **246 passed / 3 skipped / 0 failed**。

## 抓到并修掉的真机问题

CPU 上测不出来的三个，全是设备错配：

| # | 现象 | 位置 | 修法 |
| --- | --- | --- | --- |
| 1 | 量化后词嵌入报 index 在 cpu、权重在 cuda | `trainer._batch` | 批取时按模型设备搬过去 |
| 2 | LoRA 的 A/B 建在 CPU，卡上矩阵乘直接炸 | `trainer` 挂件之后 | 挂完把模型搬到基座设备 |
| 3 | 交叉熵的累加器是 CPU 张量，`+=` cuda 结果报两台设备 | `trainer.cross_entropy` | 改用 `logits.new_zeros` 同设备 |

还有一条：非量化精度（fp32 / bf16 / fp16）从来没上过卡，一直在 CPU 上跑——`spin` 里补了设备选择，现在有卡就 `.to(cuda)`。

## 量化显存实测

同一配方（8 层、512 维、约 1200 万参数、batch 2、60 步），每 0.3 秒采一次 `nvidia-smi`：

| 精度 | 峰值 |
| --- | --- |
| fp32 | 892 MiB |
| int8 | 848 MiB |
| nf4 | 796 MiB |

这个量级上量化只省一成，因为权重本身占比被激活稀释了。要看出量化的意义得把模型放大到几十亿参数，本轮没做。

## 多卡

单卡机器上用 `devices: [0, 0]` 起两个进程，验证的是分布式代码路径而不是真并行：

- `--launch torchrun` + `strategy: ddp`，20 步完成，loss 1.78
- 同参数改 `strategy: fsdp2`，20 步完成，分片存盘正常

这条路上又踩了一个：`devices: [0, 0]` 时第二个进程 `set_device(1)` 越界（error 101），改成按卡数取模绕回就通了。

续训在这条路上也真跑了：ddp 跑 10 步、每 5 步存一档，`--resume` 接上后到 15 步，`step-000015` 落地。真 nccl 与两张以上的卡仍然没跑。

## 去重索引压测

`tests/stress_index.py` 二十万条：纯内存峰值 3536.8 MB、落盘 349.7 MB，**10.1 倍**，热层封在 48628 条，落盘比纯内存慢一倍（51.8 秒 vs 101.9 秒）。

百万条（造数改成先落 124 MB 语料文件，再两个子进程读同一份）：纯内存峰值 **16479 MB**、落盘 **2098 MB**，内存比 7.9，热层峰值 47639 条（没越过 5 万的上限）。纯内存 368 秒，落盘 1016 秒。

两条读数：热层管得住，规模翻五倍也没破线；但落盘侧的内存从二十万的 350 MB 涨到 2 GB，说明还有随条数增长的部分（桶表与转冷时的键缓冲），二十万那一档的 10.1 倍到百万掉成 7.9 倍，是这部分稀释出来的。

改造（桶表分片落盘 + 转冷按 2000 条批刷 + 后台线程 + 片放大到 50 万 + 可关压缩）后重测二十万：内存比 **11.9~12.0**、落盘峰值 **296.9 MB**，都比改造前好。

异步之后主流程确实不被挡：一百一十万条，一百万之前稳在 **790 条/秒**（同步版过百万就掉到几十条）。但过了一百万还在连续转冷，一百一十万跑了四十多分钟没跑完——异步解开的是阻塞，没解开转冷本身的开销。

但一百二十万那次跑不下去：过了一百万进入连续转冷之后，三十分钟连十万条都没走完，卡在转冷段。清理完后二十万的数好看，**转冷吞吐是真正的瓶颈**，比内存涨更要紧——每片 20 万条都要转冷一次，写压缩片与删原片的 IO 把吞吐压到几十条每秒。
